# Known limits

Things we have run into and have **not solved** (or only reduced). Fix them later if time allows. Solved problems are not listed here; they are in the reports. Last updated 2026-11-05, from reports 01-14, the Stage 3 validation report, the Stage 4 handoff, `.omo/PROJECT_ARCHITECTURE.md` and the notes of runs 1-5 of the Mamba question.

"Where" points to the document with the evidence. "Effect" is what it costs us today. Items marked *(not re-checked)* come from an older report and I did not verify that they still hold.

## Stage 1: planner and domain anchor

| # | Limit | Effect | Status / idea | Where |
|---|---|---|---|---|
| 1.1 | The planner (LoRA on vLLM) is **not reproducible**, even at temperature 0 and with a fixed seed. The base judge model on the same server is. Root cause not verified (probably LoRA kernels). | Runs of one question start from different sub-questions; run-to-run comparisons are confounded. | Reduced: opt-in `PLAN_CACHE=true` reuses the stored plan. A merged-weights planner would avoid it but the GPU is already at 88%. | report 13 |
| 1.2 | Planner wording varies between runs: run 5 asked "what is X" sub-questions, run 3 asked comparison sub-questions; the central comparison is sometimes missing a dimension. | "Sufficient" counts are not comparable across runs. | Same as 1.1; no fix for the wording itself. | run 3, 5 notes |
| 1.3 | The planner's flat query list is spread over the sub-questions by similarity with an even share, so a sub-question can get a query that belongs to another one (Q2: "What is a large language model?" received "expert routing in large language models ..."; "How is MoE applied to LLMs?" received a general LLM query, and its three web sources were generic LLM pages with 0 findings). The planner also writes background sub-questions the user did not ask about ("What is an LLM?", "What are SSMs?") that use 20% of the budget. | Wasted slots; a "sufficient" sub-question that says nothing about the question. | Query hand-out: reduced (2026-11-05) by `QUERY_MIN_SIMILARITY` (default 0.55): a query that fits its sub-question worse is dropped and a sub-question left empty is expanded by the LLM. The threshold is a judgement from 447 stored queries (2% below 0.55); the two Q2 cases sit at 0.54, so they are caught narrowly, and a mild misfit at 0.68 still passes. Background sub-questions: measured (3 of 49 stored sub-questions, 6%), no safe rule found (similarity to the user's question picks core sub-questions), not built; see report 15. | Q2 run notes, report 02 |
| 1.4 | The domain anchor over-flags: unambiguous questions can get a broad anchor ("NLP", "machine learning") and a needless negation. | Noise only so far. | Not fixed. | report 12 |
| 1.5 | The anchor does not fully stop wrong-field papers: power-transformer papers with "deep learning" in the title still reach the shortlist (the judge rejects them but they use shortlist slots); the state-space shortlist is mostly latent-variable deep SSMs, S4/Mamba papers are a minority. | A few slots wasted, weaker background evidence. | Not fixed. | report 12, run 3 |
| 1.6 | Near-duplicate (paraphrased) sub-questions are **not merged** any more (merge is exact by default, because the embedding merge removed real questions). | Extra search time for a duplicate. | Accepted trade-off. | `test_subquestion_merge.py` |
| 1.7 | A longer domain *context* sentence in a planner prompt pulls it back to the whole question (Loop 2 therefore uses the anchor only). | Limits how much domain information the planner can be given. | Noted, not investigated further. | report 14 |

## Stage 2: retrieval and parsing

| # | Limit | Effect | Status / idea | Where |
|---|---|---|---|---|
| 2.1 | OpenAlex rate limiting: 429 on both keys, queries given up after 4 backoffs (13 warnings in run 3, 8 in run 5). Without a key the source is skipped; this was silent until the warning added after run 4. | A good query can be lost; without OpenAlex the evidence is thin (run 4: 1 of 5 sufficient, application papers instead of introductions). | More keys possible; per-key concurrency not done. | runs 3-5 |
| 2.2 | Semantic Scholar without an API key: the probe returns 429 almost every run, so the search is skipped; citation enrichment still retries and costs about 1 minute. | Lost time, no S2 papers. | Left as is by decision (the arXiv citations are needed). A key would fix both. | runs 1, 2, 5 |
| 2.3 | Scopus papers are mostly abstract-only: only 1 of 18 had parsed text in run 2; publisher pages are DOI-only. The arXiv-twin route recovers some (3 in run 4), 3 papers still had no usable text. Scopus also returns application papers rather than tutorials. | Less full-text evidence. | Partly reduced. | runs 2, 4 |
| 2.4 | Some papers cannot be downloaded: bot-blocked open access, JavaScript landing pages, closed access (19 of the 24 failed papers were still open in report 05 *(not re-checked)*). | Wasted parse slots. | Failure memory skips known-bad papers for 7 days. | reports 05, 06 |
| 2.5 | Parser limits: heuristic and English-only, stray headings, tables are pipe-syntax Markdown, equations and two-column order are whatever Docling gives, the figure extractor only captures main figures (not Figure S1, S2), Docling returned empty content for 3 of 18 papers in one audit. | Noisy chunks, missing figures. | Not fixed. | report 01, architecture |
| 2.6 | "Has full text" is only a length test (3000 characters); a parse that captured only the first page can pass. | Over-counts full-text evidence. | Not fixed. | report 04 |
| 2.7 | The embedding pre-filter floor (0.56) rejects very little (run 4: 374 of 374 cleared, run 5: 439 of 479); the shortlist cap of 20 and the weights are judgement, not calibrated. | The shortlist is mostly decided by ranking, not by the floor. | Not fixed. | runs 4, 5; report 04 |
| 2.8 | No query-level caching (reuse the papers of an earlier near-identical question). Near-identical wording can flip meaning ("reduces" vs "increases"), so it needs a high similarity threshold. | Every run repeats the search. | Not built. | report 02 |
| 2.9 | Parse time is not stable: it depends on the parse cache (23 of 25 papers came from it in run 5), so the parsing phase is not comparable between runs. | Timing comparisons are misleading. | Note when comparing runs. | run 5 |
| 2.10 | A new topic needs a full parse: Q2 parsed 26 uncached papers in 8m 07s (37% of the run), with 14 download failures (HTTP 403/410, HTML instead of PDF), the browser fallback failing 4 of 4 times and 5 papers left with no text, among them an MoE survey that is exactly on topic. | Slow first runs on a topic and missing key surveys. | Investigated: Zenodo records withdrawn (410); MDPI and Preprints.org bot-blocked (403, browser fallback fails too); Elsevier a JS redirect; one Scopus title variant of an arXiv paper that was parsed under the arXiv title. None fixable cheaply. | Q2 run notes, report 15 |

## Stage 3: summarizer, judge, coverage

| # | Limit | Effect | Status / idea | Where |
|---|---|---|---|---|
| 3.1 | The 9B judge (V2) is not exact. It still errs both ways: too strict on broad multi-part aspects, too lenient on adjacent-topic claims (subject confusion). V2.1 loosened the rule and was rejected (76% of what it added was not a direct answer). | Some aspects covered on weak evidence, others uncovered although answered. | V2 kept; levers left are upstream (aspect wording, queries) and Loop 2. | validation report 14, 15 |
| 3.2 | Judge noise: 39 of 239 pairs moved in or out of "yes" between versions with no change in the total, so an aspect at the 2-yes boundary can flip for reasons unrelated to the evidence. | A single aspect flip proves nothing. | Judge is deterministic per input on the same server; the cache keeps verdicts. | report 10 |
| 3.3 | The judge prompt and its model live **on the host**, not in this repo. The cache key contains `JUDGE_MODEL_ID` but not the prompt, so a changed host prompt with the same id silently mixes verdicts. | Wrong cached verdicts if someone forgets to change the id. | Manual discipline. | validation report 14.1 |
| 3.4 | Coverage rule is a judgement: at least 2 "yes" from at least 2 sources per aspect; the weights (1.0 / 0.5 / 0.5), `min_sources`, and the 0.6 detail threshold are not calibrated on labelled data. | "Sufficient" is a heuristic. | Revisit when there is labelled data. | report 04 |
| 3.5 | Aspect splitting can fail (invalid JSON twice: the aspect falls back to the unsplit detail) and can produce two-part aspects ("efficiency AND long-sequence") that judges mark partial. Exact merge gives about 30% more aspects and longer judge batches. | Some aspects are too broad to be covered by one claim. | Partly reduced (splitter test, report 11). | reports 11, runs 2, 3 |
| 3.6 | `MAX_JUDGE_ITEMS_PER_SUBQ` (60) trims by similarity and could empty one aspect when a sub-question has more than 10 aspects. | Possible false "uncovered". | Known, not fixed. | architecture |
| 3.7 | A finding is "verified" when its quote exists in the chunks, not when it is true. Math-heavy papers have more unverified quotes (1 of 4 and 2 of 4 in one run). | Stage 4's job, but nothing checks truth before it. | Not fixed. | reports 02, 04 |
| 3.8 | Groq digest JSON glitch (about once per run: "Expecting property name enclosed in double quotes"). One retry; if the second attempt fails too, that source's findings are lost (counted in `digest_failures`). | Slightly less evidence for that sub-question. | Detected and counted, not prevented. | runs 3, 5 |
| 3.9 | Groq free-tier rate limits: 58-99 parking events and 2-4 minutes of digest time per run; limits are per organization, so extra keys from one account add nothing. A paper kept under two sub-questions is digested twice. | Stage 3 time. | Key pool helps only with independent accounts. | reports 04; runs |
| 3.10 | Stage 3 preparation (aspect split, chunking, embedding) takes 2m 40s to 5m 30s, often the longest phase; chunk embeddings are not cached between runs. | Slow reruns. | Not built (cheapest speed-up left). | runs 3-5 |
| 3.11 | Evidence per sub-question is capped (3-5 papers, 2-3 web sources: `MAX_PAPERS`, `MAX_WEB`, a free-tier choice) and abstract-only papers can be chosen when fewer are parsed. | A sub-question can be "sufficient" on a handful of sources, sometimes on the wrong kind (application papers). | Accepted. | report 04, run 4 |
| 3.12 | The generic aspects (advantages, disadvantages, benefits, challenges) come from the planner's detail questions. Reduced (2026-11-05): `TOPIC_ASPECT` (default true) judges the sub-question's own question as the last aspect. Not verified end to end: the experiment used digests written without it (17 of 21 yes claims direct, 2 of 10 sub-questions flip to not sufficient). The digest prompt still tags definitions with an empty list. | "Sufficient" is stricter now; effect to be seen in the next runs. | Check Q3+ runs; switch off with `TOPIC_ASPECT=false` if it over-rejects. | report 15 |
| 3.13 | Digest quotes are edited by the digest model (citation markers dropped, clauses spliced), so true findings fail verification: 440 of 3,205 stored findings (13.7%) are unverified and never reach the judge. Reduced (2026-11-05): the verifier ignores citation markers, entities, typographic hyphens and Docling's parenthesis spaces and accepts elided quotes whose pieces are real (171 of 439 would now verify, estimate). Quotes that join sentences without an elision still fail (most of the rest). Snapping to the nearest passage was rejected (only the top band met the rule). | About 8% of findings are still lost. | The remaining lever is the digest prompt, untested (it would invalidate the digest cache). | report 15 |
| 3.14 | One Groq key can be parked for a very long time (one park of 1908 s in Q2), leaving three keys for the rest of the run. The park is in memory only, so a new process tries the key again. | Slower digests; later runs the same day may be starved. | Check Groq usage before a batch of runs. | Q2 run notes |

## Loop 2 and later stages

| # | Limit | Effect | Status / idea | Where |
|---|---|---|---|---|
| 4.1 | **Loop 2 is not built.** Only the query step exists (`gap_queries.py`). There is no loop, no ladder steps 1-2 (re-select chunks, next-ranked papers), no stop rule, no wiring into the graph. | Uncovered aspects stay uncovered. | Next step. | report 14 |
| 4.2 | The query step has not been shown to find better papers; only that its queries are valid, new and on topic. | 4.4 | **Stage 5 (report) is not built**; its contract with Stage 4 is not defined. API routers and frontend are not started. | No final answer is produced. | Not started. | architecture |
